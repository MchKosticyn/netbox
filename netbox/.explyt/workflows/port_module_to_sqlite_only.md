### Tags
`#dev`, `#python`, `#django`, `#sqlite`, `#refactoring`, `#debugging`, `#ipam`

### Goal
Портировать подсистему/модуль на «чистый SQLite»: устранить все PostgreSQL‑специфичные операции (операторы inet/cidr, jsonb‑функции, DISTINCT ON, RawSQL с кастами, Postgres‑индексы), заменить на эквиваленты или совместимые для SQLite решения, обеспечить прохождение тестов.

### Scope
- Работать в рамках выбранного модуля/подсистемы и файлов, открытых в окружении. Если нужны правки вне текущего модуля, запросить подтверждение.
- Допускается добавление локальных SQLite‑совместимых функций (UDF) и утилит, если это упрощает замену Postgres‑операторов.
- Не изменять бизнес‑логику, только совместимость с SQLite: поля, лукапы, аннотации, агрегаты, миграции, middleware/view SQL‑вызовы.

### Steps
1. Инвентаризация PostgreSQL‑специфики
   - Просканировать модуль на следующие конструкции:
     - Операторы inet/cidr: `>>`, `<<`, `>>=`, `<<=` и HOST/INET/FAMILY/MASKLEN/CAST(... AS INET)
     - JSONB/RAW SQL: `jsonb_set`, `-'key'`, касты вида `'null'::jsonb` и т.д.
     - `DISTINCT ON (...)` и иные Postgres‑особые SQL/индексацию (Gin/Gist/opclasses)
     - Импорты `django.contrib.postgres.*`
   - Составить список файлов/строк с точными вхождениями.

2. План замены под SQLite
   - inet/cidr‑операции: либо
     - Заменить на вызовы SQLite UDF (зарегистрировать функции `INET_CONTAINS`, `INET_CONTAINS_OR_EQUALS`, `INET_CONTAINED`, `INET_HOST`), либо
     - Упростить/обнулить аннотации, если это косметические подсчёты (например, заменить на `Value(0)`).
   - JSONB: заменить на функции JSON1 (`json_set`, `json_remove`) и безопасные значения (`Value(None, JSONField())`, `Coalesce(..., Value({}, JSONField()))`).
   - DISTINCT ON: заменить на `distinct()` с корректным `order_by()` или переписать запрос.
   - Postgres‑индексы/RawSQL: удалить или заменить на ORM/SQLite‑совместимые выражения.

3. Реализация
   - Внедрить UDF в едином месте инициализации соединения SQLite (через сигнал `connection_created`).
   - Переписать лукапы модуля на использование UDF/JSON1 или упростить их (с поясняющим комментарием).
   - Заменить Postgres‑RawSQL на ORM-аннотации или `Value(...)` там, где точность не критична для UI.
   - Удалить `django.contrib.postgres` импорты; заменить поля на `models.JSONField`/`TextField` при необходимости.

4. Проверка и итерации
   - Запустить тесты только для модуля и/или целевые кейсы, зафиксировать ошибки.
   - По ошибкам найти оставшиеся Postgres‑следы и повторить шаги 2–3.
   - После стабилизации — прогнать смежные модули (например, core), чтобы исключить регрессии.

#### Как запускать тесты и собирать логи
- Базовые команды (выберите нужную):
  - `source .venv/bin/activate && python manage.py test <module>` — прогон всего модуля.
  - `source .venv/bin/activate && python manage.py test <dotted.test.path>` — точечный тест/кейс.
  - `source .venv/bin/activate && python manage.py test <module> --keepdb` — быстрее за счёт сохранения тестовой БД.
  - Добавьте `| tee <logfile>` для сохранения вывода в лог.
- Примеры:
  - `source .venv/bin/activate && python manage.py test ipam --keepdb | tee ipam_test.log`
  - `source .venv/bin/activate && python manage.py test core.tests.test_views.ObjectChangeTestCase.test_objectchange_list | tee core_case.log`
- Полезные флаги:
  - `-v 2` — увеличить подробность вывода.
  - `--pattern="test_*.py"` — ограничить паттерн файлов.
- Где искать логи/артефакты:
  - Сохраняйте лог‑файлы в каталоге проекта (например, `ipam_test.log`, `core_test.log`).
  - При необходимости используйте отдельную папку `logs/` и прикладывайте путь в отчёт.
- Диагностика миграций:
  - `source .venv/bin/activate && python manage.py showmigrations <app>` — статус миграций.
  - `source .venv/bin/activate && python manage.py migrate <app> --plan` — план применения.

5. Документация изменений
   - Внести краткие комментарии в код в местах упрощений (почему обнулена аннотация/чем заменён оператор).
   - Составить краткий отчёт: где и что заменено, какие UDF добавлены, какие тесты покрывают изменения.

### Output
- Список затронутых файлов с кратким описанием произведённых замен.
- Вывод тестов модуля (ключевые ошибки до и после, подтверждение прохождения).
- Краткие комментарии по UDF/JSON1 и упрощённым аннотациям (что было и что стало).
