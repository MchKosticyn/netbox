### Tags
`#dev`, `#python`, `#django`, `#testing`, `#debugging`, `#redis`, `#rq`, `#fakeredis`

### Goal
Заменить внешнюю зависимость Redis/RQ на in-memory shim, совместимый с используемым API (например, django_rq), чтобы тесты и локальный рантайм работали без внешнего сервиса, сохранив поведение очередей, ожидаемое тестами.

### Scope
- Менять только вспомогательную инфраструктуру фоновых задач: shim модулей очереди/соединения и минимальные интеграции.
- Не менять бизнес-логику и обработчики задач; только подмена провайдера очереди и совместимость интерфейсов.
- Сохранить существующие точки интеграции (импорты и вызовы API), реализовав их в shim.
- Если потребуются правки вне этой области (например, в местах вызова), сперва запросить подтверждение.

### Steps
1. Уточнить требования
   - Спросить у пользователя:
     - Какие именно API очереди используются (модули/функции/методы), например: get_queue, enqueue, jobs, count, empty, get_worker, job-декоратор.
     - Нужны ли именованные очереди и постоянное соответствие имени -> экземпляр очереди.
     - Какой порядок задач ожидают тесты (FIFO по моменту enqueue, либо по полю из payload).
     - Нужно ли имитировать соединение Redis (get_connection/get_redis_connection) и статистики (get_statistics).

2. Спроектировать shim
   - Выбрать основу: простая in-memory реализация с optional fakeredis (без внешнего сервиса).
   - Описать минимальные классы/функции:
     - FakeQueue: свойства/методы jobs (список задач), count (целое), enqueue(func, *args, **kwargs) -> Job, empty().
     - Job (dataclass): id, func_name, args, kwargs, status; хранить копию kwargs, чтобы изменения извне не влияли на сохранённую запись.
     - Функции уровня пакета: get_queue(name), get_connection(), get_redis_connection().
     - Необязательные: get_worker()/Worker, job-декоратор (no-op), get_queue_by_index, простая статистика.
   - Гарантировать стабильный порядок:
     - По умолчанию FIFO (порядок enqueue). Если тесты сравнивают с данными ответа, допускается вторичная сортировка по идентификатору из payload (обсудить и зафиксировать).

3. Реализация shim (минимальная совместимость API)
   - Создать модуль/пакет shim, импортируемый под тем же именем, что и используемая библиотека (например, django_rq), и пробросить требуемые функции/классы.
   - Реализовать get_queue с кэшированием по имени/индексу, чтобы разные вызовы одного имени возвращали один и тот же объект.
   - В enqueue:
     - Генерировать уникальный id для Job.
     - Сохранять deepcopy(kwargs) и, при необходимости, метки времени/порядка для сортировки.
     - Не выполнять задачу автоматически (счётчики должны отражать очередь, а не выполнение).
   - Предусмотреть методы count и empty для тестов.

4. Интеграция
   - Переключить импорт в проекте на shim-пакет (либо разместить shim так, чтобы он перехватывал импорт, либо заменить импорты точечно — по согласованию).
   - Если проект ожидает настройки очередей/карт, обеспечить константы (например, QUEUES_LIST/QUEUES_MAP) и простое сопоставление имён.
   - При необходимости переключить Django-кеш/брокер на локальную (in-memory) реализацию для тестов.

5. Синхронизация поведения с тестами
   - Запустить точечные тесты, которые проверяют постановку задач и порядок.
   - Если ассерты завязаны на порядок элементов в jobs, подстроить стратегию выдачи (FIFO/сортировка по полю payload) и зафиксировать её в комментарии.
   - Добавить недостающие методы (например, get_jobs()), если они требуются тестами, с корректной семантикой (обычно эквивалент jobs).

6. Прогоны тестов
   - Команды запуска (из-под virtualenv):
     - `source .venv/bin/activate && python manage.py test <dotted.test.path> -v 2 --failfast`
     - `source .venv/bin/activate && python manage.py test <app_or_module> -v 2`
   - Сначала запускайте минимальные тесты, связанные с очередями, затем расширяйте охват (по модулям).
   - При падениях фиксируйте конкретный недостающий метод/несовпадение поведения и дорабатывайте shim минимально.

### Output
- Краткое описание реализованного shim: список доступных API и их соответствие оригиналу.
- Перечень затронутых файлов и обоснование изменений.
- Подтверждение прохождения релевантных тестов: что запускалось и каков результат.
- Если были адаптированы правила порядка выдачи задач — явное описание стратегии (FIFO/сортировка по payload) и почему она выбрана.
